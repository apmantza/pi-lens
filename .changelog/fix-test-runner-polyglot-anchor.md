- **Resolve the test runner per file, not per repository root, and never hand a runner a language it does not declare** — `detectRunner(cwd, file)` read the config files at the repository root only, so in a repo holding two or more languages the winner was decided by the declaration order of `RUNNERS` and every other language was handed the wrong one: with a root `go.mod` declared before `gradle`, a `.java` file under `src/test/java/` was treated as its own test target and passed to `go test`, which answered `FAIL <pkg> [setup failed]` — a runner error on every Java edit in a polyglot monorepo, indistinguishable from a real failure. The runner now comes from `resolveProjectAnchor`, which walks upward from the file's own directory to `cwd` and takes the NEAREST directory declaring a runner whose new `exts` field lists the file's extension; when nothing on the way up serves that language the answer is `null` (no target) instead of a guess. This is the test runner's own sync analogue of the LSP subsystem's `NearestRoot` — nearest project root, bounded by a stop dir. Nested modules get the same treatment: a repo carrying several `go.mod` files now anchors each `.go` file at ITS module rather than the root. Because the `gradle`/`maven`/`cargo`/`dotnet` `args()` ignore the target file and run the WHOLE project, those runners carry `perFileTargetable: false` and are only used when the edited file belongs to the project rooted at `cwd` — otherwise a single module's edit would compile and test every module. A file outside the project root keeps the legacy root-based resolution, because `getTestRunTarget` must still return a target there for the built-in exclusion layer to fail closed on (#2522). `exts` is the single source of truth: both the language gate and `RUNNER_SUPPORTED_EXTS` are derived from `RUNNERS`, so they cannot drift apart the way this subsystem's language tables have before (#1545, #657).
